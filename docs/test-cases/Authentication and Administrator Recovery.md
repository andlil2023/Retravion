# Authentication and Administrator Recovery — Test Specifications

This design is provisional. It specifies verification intent, not implemented tests or successful verification results.

**Requirements:** [Authentication and Administrator Recovery](../requirements/Authentication%20and%20Administrator%20Recovery.md)

## Verification Method and Automation Status

- **Verification method:** Automated or Manual.
- **Automation status:** This specification is a verification plan, not an inventory of completed automation. Initial-setup and post-recovery password-confirmation scenarios have focused integration coverage, but not every step of TC-AUTH-015 is automated. Manual verification has automation status Not applicable.
- A Yes value in Automation candidate identifies proposed Automated verification. A No value identifies Manual verification.
- No automated test code has been implemented as part of this specification.

## Test Cases

TC-AUTH-023–TC-AUTH-038 are proposed verification specifications, not implemented or executed tests. Run applicable creation, availability, and reset scenarios separately for ordinary and administrator target accounts; the acting administrator and target are different accounts except in self-operation rejection cases. Ordinary-account creation does not imply product access, which is outside this design.

## Coverage Gaps and Unresolved Ambiguities

- **Password confirmation:** [PBI #39](https://github.com/andlil2023/Retravion/issues/39) tracks the confirmation requirement and implementation. `tests/Retravion.IntegrationTests/PasswordReplacementTests.cs` covers initial-setup rejection and matching success, including missing or empty new passwords and Unicode-normalization mismatches. `tests/Retravion.IntegrationTests/AdministratorRecoveryCommandTests.cs` covers post-recovery direct POST rejection of omitted, empty, case-mismatched, and whitespace-mismatched confirmation, retained restrictions and credentials, and matching success; it requires PostgreSQL. TC-AUTH-015 also specifies post-recovery field checks, missing or empty new passwords, Unicode-normalization mismatches, and form-level scenarios that this recovery test does not separately cover.
- **“Any user interaction”:** Concrete interaction examples need to be identified when the application behavior is designed.
- **Recovery authority:** TC-AUTH-017 needs the selected recovery mechanism and permission boundary before its executable procedure can be completed.

- **Account-administration automation:** TC-AUTH-023–TC-AUTH-038 describe verification intent only. Concrete routes, fixtures, supported UI interactions, and executable assertions await implementation planning; these cases provide no evidence of passed behavior.
- **Cryptographic randomness:** Generated samples cannot prove randomness security; TC-AUTH-037 requires inspection of the selected randomness source and its use.
- **Inactivation sessions:** Immediate termination of existing sessions is not required. TC-AUTH-029 must not demand either session survival or immediate termination. Reset is different: TC-AUTH-033 requires immediate invalidation.

## Deferred Tests

- Concrete recovery-command, password-hashing, and protected-entry-point checks await implementation design.
- Executable account-creation, availability, and administrator-reset tests await the feature implementation plan; their verification intent is specified above.
- Product-scoped permissions and audit-trail tests remain outside this account-administration design.
